# 上秤 · 测试站备份恢复与运行检查

更新：2026-10-14（北京时间）。适用于当前合成数据联机测试站；部署概况见[联机测试部署](联机测试部署.md)，本批证据见[开发记录](本地基础版开发记录.md)。真实数据的保留、删除重放及生产运行承诺仍需另行冻结。

## 已安装的能力

| 项目 | 行为 |
| --- | --- |
| 独立运维工具 | `/opt/payathon-ops/current` 指向独立发布目录；不替换 `/opt/payathon-test/current` 或重启应用 |
| 自动备份 | `payathon-backup.timer` 每小时触发，随机延迟不超过 2 分钟；开机补执行错过的日历任务 |
| 备份位置 | `/var/backups/payathon-test/<UTC 时间与随机编号>/`；目录 0700，文件 0600，由非 root 的 `payathon-test` 执行 |
| 备份内容 | 一致性 SQLite 快照、账号摘要配置、环境配置、对应应用源码包、校验与恢复报告；不含本地开发库、体验码明文或 Git 历史 |
| 每份恢复验证 | 临时目录核对全表摘要、完整性与外键，再从包内源码启动仅本机随机端口，逐账号读取本人、小组、记录、历史及支持请求；临时会话只存在于恢复副本，结束后删除整个演练目录 |
| 故障检查 | `payathon-monitor.timer` 每 5 分钟触发；检查结果写入私有 `/var/lib/payathon-monitor/status.json`，异常／恢复变化记入 journal，异常退出码非零 |
| 服务器外副本 | 经用户明确确认，本次下载一份到本机私有 `var/test/backups/`，并在本机从包内源码恢复验证成功；目前不是自动异地同步 |

一致性快照使用 [Node 24 SQLite backup API](https://nodejs.org/download/release/v24.19.0/docs/api/sqlite.html#sqlitebackupsource-db-path-options)，不直接复制使用中的主文件。只将新建快照切为 DELETE 日志模式，成为不依赖 WAL／SHM 的单文件；在线库继续使用原 WAL。备份必须完成校验及恢复读取后才原子发布目录，失败不留下可被识别为成功的备份。最新完成包损坏时直接报错，不用较旧包掩盖异常。

源码包限定 `apps/`、`packages/`、`db/`、`package.json`、锁文件和 Node 版本文件；配置独立保存，不输出内容到日志。已部署工具仍为此前版本；本批本地工具新增结构 1／2 兼容，不在备份时自动迁移源库。

### 本地新增的注销恢复保护（尚未部署）

结构 2 的业务库通过 `privacy_meta` 绑定独立删除清单（默认 `DATABASE_PATH.deletions.sqlite`）。注销先持久提交清单，再清理在线表；重启补处理未完成事件。新版快照恢复必须提供同一来源的**最新清单**，不能把旧清单随快照一起回滚；恢复工具只读清单，在临时副本重放后才启动业务访问。文件缺失、身份不符或已知序号落后时拒绝启动；操作人员仍需保证提供的是最新副本，工具不能证明外部副本的新鲜度。

本地示例（路径按实际私有文件填写）：

```sh
DELETION_JOURNAL_PATH=/private/path/live.sqlite.deletions.sqlite node scripts/backup.mjs drill /private/path/backup-directory
```

`create` 使用配置的清单路径，未配置时使用源库旁的默认路径；`drill` 可从 `DATABASE_PATH` 推导默认路径。清单不装入可回退的快照包，当前也没有自动异地保存或轮换；上线前必须落实独立持久化、加密和淘汰规则。旧结构 1 的合成备份兼容恢复不会凭空补回过去未记录的注销事件；有当前清单时必须显式传入。此次只演练合成账号注销，未实现某期删除或旧备份物理清除；独立撤回共享已按用户决定移出范围。

## 检查范围与阈值

- 应用、Nginx、证书续期及两个运维定时器处于 active；最近一次备份任务结果为 success。
- 本机及公网 HTTPS 健康接口返回 `ok:true, storage:true, mode:test`；每次请求超时 8 秒，拒绝跳转与错误模式。任一样本超过 2 秒标记慢检查，仅为运维探测阈值，不是 API p95 或容量承诺。
- TLS 证书可信、匹配主机，剩余不足 24 小时标记异常。
- 最新完成备份的文件 SHA-256、数据库全表摘要、结构、完整性及外键通过，且有成功恢复报告；从备份开始计时超过 2 小时或时间异常则报过期。
- 数据盘可用空间至少 256 MiB，且不少于总量的 5%。当前备份与数据库在同一服务器磁盘；磁盘检查覆盖该盘，不代表其他存储也被检查。
- 最近 6 分钟应用日志中的非预期异常和到期任务错误进入异常状态；日志读取失败也报错。当前不是所有业务拒绝／客户端失败的统计，没有收集身体数值。

这套检查在服务器本机运行，能检查本机访问公网入口的路径。没有配置短信、邮件、聊天通知或独立外部探针；整台服务器停机时无法自行报信。当前状态可按下面命令查询。暂不自动清理备份；正式保留与删除策略明确后再启用清理，避免把测试默认值作为真实数据政策。

## 查询和手动验收

先按[部署说明](联机测试部署.md)连接服务器，以下命令在服务器执行：

```sh
systemctl list-timers payathon-backup.timer payathon-monitor.timer
systemctl show payathon-backup.service --property=Result
cat /var/lib/payathon-monitor/status.json
journalctl -u payathon-backup.service -u payathon-monitor.service -n 30 --no-pager
```

手动生成一份备份（不重启应用），完成后刷新检查：

```sh
systemctl start payathon-backup.service
systemctl start payathon-monitor.service
```

再次从最新完成包恢复到临时目录：

```sh
cd /opt/payathon-ops/current
BACKUP_ROOT=/var/backups/payathon-test /opt/payathon-tools/node-v24.19.0-linux-x64/bin/node scripts/backup.mjs drill
```

演练“备份不可用 → 检测失败 → 正常恢复”使用空的临时备份目录和临时状态文件，不停止应用、不修改实际备份或实际监测状态：

```sh
cd /opt/payathon-ops/current
BACKUP_ROOT=/var/backups/payathon-test /opt/payathon-tools/node-v24.19.0-linux-x64/bin/node --env-file=/etc/payathon-test/app.env scripts/operations-drill.mjs
```

上述恢复命令只接受备份源，不接受在线数据库作为写入目标。本机也可用 README 中的 Node 执行 `scripts/backup.mjs drill <私有备份目录>`，临时服务只监听本机。配置文件和快照均属于私有备份，不能提交 Git、放进公网目录或分享给体验者。

## 故障处置与实际切换

1. 先读状态中的 issues 和对应 journal。服务／HTTPS 故障检查应用、Nginx 和证书任务；备份失败检查任务日志、磁盘与文件权限；慢检查先辨别本机和公网路径。不要以删除数据库、重建账号或重复申请证书来恢复。
2. 记录故障时间、受影响范围与最后有效备份开始时间。RPO 是可能丢失的数据时间，不能用“备份每小时”直接承诺；本批未测完整故障停机与换机 RTO。
3. 实际恢复前暂停写入并保留故障库与配置。选定校验成功的包，先跑隔离恢复，再核对快照后已注销／删除的处理，不能恢复旧快照后让已删除数据重新共享。
4. 在新私有目录解开包内应用源码，用清单所记 Node 版本恢复运行时，保留原账号映射。环境配置只作恢复参考，重新核对数据库路径、origin、端口及 HTTPS，先以隔离配置验收。应用源码包不含 Node、Nginx、证书私钥或操作系统镜像；新主机仍需重建这些设施。
5. 验收本人身份、成员关系、记录和历史，确定切换点和回退点后再切换在线配置、重启并检查公网。当前未执行在线库替换或新主机接管；发生真实事故时按当次状态执行，不把临时恢复等同于已完成整站灾备。

## 运维工具更新

运维发布与应用发布独立，源码包及测试不含 `var/`、私有配置、凭据或 `.git/`。在本机项目根目录打包：

```sh
COPYFILE_DISABLE=1 tar --no-xattrs -czf /tmp/payathon-operations.tgz apps packages db scripts tests deploy package.json package-lock.json .node-version
```

按已授权主机及目录上传，再在服务器提取 `deploy/install-operations.sh` 并用 Bash 执行。安装脚本在候选目录运行语法、全部测试及 systemd 配置验证，通过后更新运维工具和两个定时器，立即做一次备份与检查。已有数据库、账号配置、应用发布和 HTTPS 不由此脚本改写。应用结构变化时同步更新运维包，避免使用不兼容的检查器。
