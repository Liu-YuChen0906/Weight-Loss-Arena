# 11 Redis 使用方案：会话、缓存与限流

更新：2026-10-30。本文是 Redis 的用途边界与决策依据；实时动态的完整设计见 [12 实时动态与事件推送](12-实时动态与事件推送.md)。

**状态：共享会话已实现并验证；实时事件推送、统计缓存、限流迁移、A／B／C 压测均未实施。** 验收见 [06 验收矩阵](06-验收矩阵.md) 的 P01–P08 与 R01–R08，简历写法见第 7 节。**第 7.4 节的数字模板在实测前不得填写、不得使用。**

## 1. 结论：四个用途，两个必需

| 用途 | 解决什么 | 为什么是这个 | 状态 |
| --- | --- | --- | --- |
| 共享登录会话 | 两个实例读到同一份登录态 | 会话必须跨进程共享，单实例内存做不到 | 已实现 |
| 实时事件广播 | 一个实例上的写入，要推给连在另一个实例上的用户 | 实例彼此不知道对方持有哪些连接，必须有一个共享通道 | B10，见 [12](12-实时动态与事件推送.md) |
| 统计缓存 | 少算几次快照 | **不是必需品**，是可测量的容量实验 | B9 可选 |
| 登录与接口限流 | 高频尝试的原子计数 | 原子计数加 TTL，省掉每次尝试一次 MySQL 事务 | B9 可裁剪 |

判断标准只有一条：**MySQL 是事实来源，Redis 只存"删掉也能从 MySQL 重新算出来"或"本来就允许丢"的东西。** 体重记录、准备状态、删除清单、付费短信额度都不放进 Redis。

反过来说清楚：如果本项目只有一个实例，前两条都不成立，正确选择是本地缓存而不是 Redis。**引入 Redis 的真正理由是两个实例要看到同一份状态**，缓存只是顺带的收益。

## 3. 统计缓存：先说清楚它不是必需品

### 3.1 现状不是"算得慢"

本机一次性微基准用真实的 `Domain.stats` 跑了 8 人 × 90 条 × 2 套统计（单机、单次、未纳入证据清单）：

```text
每份快照的统计计算 ≈ 0.11 毫秒
```

而记录查询是 `(room_id, user_id)` 主键前缀的范围扫描，最多 90 行，是最便宜的一类访问。**单次快照本来就不慢。**

### 3.2 真正的成本来自"反复拉"

前端在小组、记录、分析、数据页前台每 5 秒拉一次**整份快照**（见 [02 页面与交互](02-页面与交互.md) 的刷新约定与 [App.vue](../apps/web-vue/src/App.vue) 的 `poll()`）。一份快照包含每个成员的范围点、全期统计、曲线点和记录明细，8 人约几十到一百 KB。

于是：8 人在线 × 12 次／分钟 = **96 次完整快照／分钟**，每次都要做 10 条左右 SQL，绝大多数时候什么也没变。这是流量和空转问题，不完全是数据库问题。

### 3.3 所以缓存的定位

- 它降低的是"事件触发后那一次刷新"的成本，**不是**让页面变快；
- 它的收益必须靠 A／B／C 对照测出来；
- 如果测不出显著收益，**不上线也是合格结论**，并如实记录。

缓存的价值在于设计本身：版本键、失效矩阵、并发重建、故障回源，这些是能在面试里讲透的东西，而不是"提升了百分之多少"。

## 4. 缓存设计（B9，可选）

### 4.1 缓存什么

缓存整个 `Snapshot` 响应体（JSON），一次往返取回。不缓存：用户资料、身高、手机号、历史列表。

不用 Hash 拆字段：要多取几次，还要处理字段版本不一致。不用 JDK 序列化：JSON 可读、跨版本、并能复用"无身高无手机号"的断言。

### 4.2 Key 设计

```text
shangcheng:java:{mode}:room:snapshot:{roomId}:{statsVersion}:{businessDate}:{range}
```

| 片段 | 作用 |
| --- | --- |
| `{mode}` | local／test／sms-trial 环境隔离 |
| `{roomId}` | 房间 |
| `{statsVersion}` | 数据版本，来自 MySQL `rooms.stats_version`，失效的核心 |
| `{businessDate}` | 北京时间日期；跨日后完成率、剩余天数会变，没有写入也要换键 |
| `{range}` | 7／28／90，不收敛会串数据 |

不把 userId 放进键：快照对同房间、同 range 的所有成员完全一致（`userId` 只用于鉴权，不影响响应）。这条性质必须由测试守住；将来若加入"仅本人可见"的字段，要么移出公共缓存，要么把用户维度加进键。

注销需要立即清除时，用键索引集合精确删除，替代 SCAN／FLUSHALL：

```text
shangcheng:java:{mode}:room:snapshot:keys:{roomId}     （Set，成员是有效缓存键）
```

### 4.3 失效：写版本，不删缓存

所有会改变响应的写入，都在同一个 MySQL 事务里执行 `UPDATE rooms SET stats_version = stats_version + 1 WHERE id = ?`：

| 写路径 | 改变的响应内容 | 落点 |
| --- | --- | --- |
| 新增／覆盖体重记录 | 统计、曲线、排名、当日记录 | `WeightRecordService.save` |
| 加入／退出／重新加入 | 成员列表、排名、名额 | `RoomService` 加入与退出手续 |
| 准备状态、身高／起始体重／目标 | `ready`、起点、曲线起点 | `RoomService` 准备与编辑 |
| 改名／介绍／周期／强度 | `room`、全员分母 | `RoomService` 编辑 |
| 开始／到期／关闭／取消／交接 | `status`、`startDate`、`remaining` | `RoomService` 生命周期方法 |
| 昵称／头像 | 成员昵称、头像 | `UserService.updateProfile`，需 bump 该用户仍有有效成员关系的全部房间（含 ENDED） |
| 注销 | 全部 | `PrivacyService.delete`：bump 版本并删除缓存键与索引 |

两条容易漏的：**昵称和头像**（跨房间，影响别人看到的快照）和**跨日**（没有写入，但完成率会变，靠 `businessDate` 进键解决）。

### 4.4 不复用 `rooms.version`

`rooms.version` 现在承担客户端乐观锁：`RoomService.java:98` 用请求里的 version 校验，保存记录也会 `version + 1`。它的语义随客户端协议变化，缓存正确性不能挂在另一个功能的字段上。

新增独立列 `stats_version BIGINT UNSIGNED NOT NULL DEFAULT 0`，走新的 Flyway 迁移（V1 已执行，内容不得修改）。这个列同时是版本轮询接口的依据（见 12 第 7 节），所以它不是只为缓存而加。

### 4.5 读流程

1. 鉴权、到期检查。**缓存命中不能跳过鉴权。**
2. 读房间行取 `stats_version`、`status`、`start_date`、`days`——本来就要做，不额外增加往返。
3. 计算业务日期并校验 `range ∈ {7,28,90}`。
4. 拼键，`GET`。
5. 命中：反序列化返回。
6. 未命中：获取该键的重建锁；拿到后**再查一次**缓存，仍缺失才批量查询、计算、写入，并登记到键索引。
7. 写缓存前复查 `stats_version` 未变；变了就放弃写入，旧数据不进入任何键。

### 4.6 并发重建（单飞）

- Redisson `RLock`，键 `...:room:snapshot:lock:{roomId}:{statsVersion}:{range}`，`tryLock(200ms, 3s)`，只由持有者释放。
- 没拿到锁：等待不超过 200ms 重读；仍未命中就直接回源，不做无限等待。
- 回源并发上限：每实例 `Semaphore(2)`，取不到短暂等待后回源（读接口不返回繁忙）。
- 锁只减少重复计算；正确性由版本键保证。即使两个实例同时重建，也只是多算一次。

### 4.7 TTL 与容量

- 快照 TTL 从 **60 秒 + 0–15 秒随机抖动**起步，属待压测确认的初始参数。
- 键里带版本，TTL 只负责回收旧键，**不承担"写后及时更新"**。
- 容量：8 人 × 90 天约 20 KB／键；键数 = 活跃房间 × 3 个 range × 存活版本数。
- 不配置 `allkeys-lru`：会话与缓存共用实例，全键淘汰会误伤会话；按房间数估算容量，不设淘汰。

### 4.8 版本键为什么能替代"删缓存"

经典竞态：请求 A 读到旧数据 → 写入方提交并删缓存 → A 把旧结果写回，旧数据长期驻留。

版本键把它从时序问题变成命名问题：A 只能写**旧版本键**，新请求永远读**新版本键**；旧键等过期。因此不需要"先删缓存再写库"，也不需要跨实例失效广播。代价是短时间内可能同时存在 2–3 个版本的键。

### 4.9 故障边界

- 缓存读写异常：捕获、记 WARN 和计数、回源，读接口不因缓存故障失败。
- 连续失败若干次后熔断 30 秒内跳过缓存：否则每个请求都要等满 2 秒超时，缓存故障被放大成整体变慢。
- Redis 整体不可用：Session 先失败，认证接口返回明确 503。**不能宣传"Redis 挂掉不影响应用"。** 统计缓存可以回源，但登录不行，两件事分开验证（I03、P05）。
- 恢复：无需预热，首个请求自然回源。

### 4.10 隐私

- 缓存内容就是已脱敏的响应投影：没有身高、手机号、CSRF。
- 注销：bump 版本、按索引删除该房间全部缓存键、删除索引集合。**不使用 SCAN，更不用 FLUSHALL。**
- 迟到的重建任务在写缓存前复核注销状态与版本，删除后不得写回。

## 5. 限流（可选，可裁剪）

现状：`RateLimitService` 用 MySQL 事务 + 行锁，每次登录尝试一次写事务。

迁移后：`INCR` + `EXPIRE` 用 Lua 一次执行，键 `...:rate:{scope}:{subject}:{windowStart}`，用剩余 TTL 作 `retryAfter`。两个实例共用计数，额度不会被各算一份；付费短信日额度仍走 MySQL 账本，Redis 不承担金额。

失败语义：Redis 不可用时拒绝，不放行（与 Session 一致）。固定窗口的边界突刺（连续两个窗口最多 2 倍）本期接受并写进文档，要更严格就换滑动窗口或令牌桶。

## 6. 验收与压测

正确性条目 P01–P08 见 [06 验收矩阵](06-验收矩阵.md)；关联的实时条目 R01–R08 见同一处与 [12](12-实时动态与事件推送.md)。

| 对照组 | 实现 | 用途 |
| --- | --- | --- |
| A | 逐成员查询，无统计缓存 | 原始基线 |
| B | 批量查询，无统计缓存 | 单独测量 SQL 改写收益 |
| C | 批量查询 + Redis 统计缓存 | 测量缓存的额外收益 |

固定条件：同一台机器、同样实例数（2）、同样数据规模、同样请求比例（读:写 = 95:5）、同样响应内容。缓存开关只控制统计缓存，三组都保留 Redis Session。

| 指标 | 采集方式 |
| --- | --- |
| P50／P95／P99、吞吐、错误率 | 压测脚本输出 JSON |
| 每次快照的 SQL 次数 | `SHOW GLOBAL STATUS LIKE 'Com_select'` 前后差值 ÷ 请求数 |
| 缓存命中率、重建次数、锁等待 | 应用内计数器，结束时导出 |
| 数据库负载 | MySQL CPU 与连接池等待（无则写"未采集"） |
| 响应一致性 | A／B／C 三组响应逐字段比对（去掉 requestId） |

**当前结果：A／B／C 未执行，任何耗时、吞吐、SQL 降幅、命中率数字都不存在。** 如果 B 已解决瓶颈、C 没有额外收益，就如实写"缓存无显著收益，未上线"。这也是合格结论。

### 7.1 现在就能写（已验证）

### 7.5 禁止写法

- 不写"支撑 X 万用户／X 千 QPS"：单节点演示，没有容量结论。
- 不写"缓存命中率 99%／性能提升 300%"：未测的数字一个都不写。
- 不写"Redis 集群／哨兵／高可用"：单节点，没有主从。
- 不写"消息队列保证不丢不重"：事件推送是**允许丢**的，M2 的 MQ 也只承诺至少一次加业务幂等。
- 不写"实时消息必达"：事件只是提示，不是数据源。
- 不写"高并发架构"：可以说"两个实例"，不能说"高并发"。

### 7.6 面试问答（缓存部分；实时部分见 12）

1. **为什么用 Redis 不用 Caffeine？** 两个实例，本地缓存各存各的，失效要广播，两边视图不一致。单实例才该选本地缓存。
2. **为什么不用 `@Cacheable`？** 需要版本键、单飞、降级、命中率观测；注解式表达不了"版本变了换键"和"旧版本写入无害"，很容易写成 evict 竞态。
3. **怎么保证数据库和缓存一致？** 不追求强一致。写事务递增版本，新请求读新键；读请求先鉴权、再读版本、再取缓存；写缓存前复查版本。能保证的是"不会把旧版本内容写进新版本键"。
4. **缓存击穿、穿透、雪崩？** 击穿：单飞锁加双检。穿透：鉴权在缓存之前，非成员和不存在房间根本不会建缓存。雪崩：TTL 抖动，版本键天然分散。
5. **TTL 为什么 60 秒？** 它不是正确性机制，只是回收；参数是待压测的起点，抖动避免同时过期。
6. **为什么说这个缓存不是必需的？** 按当前规模（8 人、90 天）单次快照的计算约 0.1 毫秒，数据库查询也是索引范围扫描，收益有限。做它是为了验证通用方法并量化，不宣称线上收益。

## 8. 不做清单（克制也是设计）

- 不做本地 + Redis 两级缓存：两实例下本地层失效要广播，收益不抵复杂度。
- 不做定时预热／定时刷新：版本键已经够了。
- 不做 Redis 集群、哨兵、主从：单节点演示，不称高可用。
- 不用 Redis 存业务事实、账单、删除清单。
- 不用分布式锁替代数据库唯一约束。
- 不把事件通道当队列用：事件不持久化、不补偿（见 [12](12-实时动态与事件推送.md) 第 11 节）。
- 不把缓存命中率做成对用户可见的指标。
