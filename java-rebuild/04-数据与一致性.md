# 04 数据与一致性

此为 Java 重构的推荐落地设计，列出的新表名是实现默认值，不冒充旧库已有结构。Flyway交付DDL；MySQL不能直接复制SQLite的INSERT OR REPLACE、部分唯一索引、PRAGMA或同步事务方式。

## 1. 业务数据模型

ID对外使用不可预测字符串（UUID等）；Unicode用utf8mb4；手机号／邀请码／幂等键比较采用明确区分大小写或规范化策略，不能依赖数据库默认排序规则。重量DECIMAL避免持久化二进制浮点误差；原始准备值的精度必须覆盖旧输入，不提前截到两位；最终记录／目标两位。时间统一UTC，业务日期DATE，业务时区Asia/Shanghai。

| 表 | 主要字段 | 约束／索引与生命周期 |
| --- | --- | --- |
| users | id,phone,nickname,avatar,consent_version,consent_at,created_at | phone唯一；头像默认🌱；currentRoomId从活动名额派生或一致维护 |
| rooms | id,name,intro,days,intensity,status,owner_id,invite_code,version,stats_version,start_date,created_at | invite_code唯一；days14–90；状态／强度枚举；(status,start_date)索引；owner在注销后可能已不存在，不设导致无法注销的强制外键；version供客户端乐观锁，stats_version仅供统计缓存失效，两者不混用 |
| members | id,room_id,user_id,state,ready,height,start_weight,target,algorithm,join_date,joined_at,joined_order | (room_id,state)、(user_id,state)索引；每次重加入新关系；有效关系唯一见下 |
| active_memberships | user_id,room_id,member_id | user_id主键；member_id唯一；最多一个未结束小组的数据库兜底；LOBBY／ACTIVE加入时写，退出／到期／注销释放 |
| records | room_id,user_id,business_date,weight,version,updated_at | 主键(room_id,user_id,business_date)，weight20–300，版本条件更新；范围查询索引 |
| idempotency | user_id,request_key,operation,body_hash,result_json,created_at | 主键(user_id,request_key)，记录成功结果；错误事务回滚不存成功回执 |
| otp_dispatches | phone,credential_marker,dispatch_id,method,delivery_state,expires_at,sent_at,attempts,verify_lease_token,verify_lease_until | phone唯一；只保留当前流水；不保存PNVS明文码，平台marker与本地hash不可互通 |
| rate_limits / sms_daily_usage | key,count,reset_at 或 business_date,count | 原子窗口计数；付费全站日额度MySQL持久化，Redis清空不重置 |
| reminder_receipts | room_id,recipient_id,member_id,round,stage,shown_date | 主键(room_id,recipient_id,member_id,round,stage)，唯一(room_id,recipient_id,member_id,shown_date) |
| support_requests | id,user_id,message,status,created_at,resolved_at? | (user_id,created_at)索引，OPEN／RESOLVED；新增resolved_at不改变用户权限 |
| privacy_meta | id,journal_id,last_sequence | 业务快照记录已处理独立删除清单位置 |

有效成员关系唯一：可以在members增加仅JOINED时取user_id的生成列，与room_id组成唯一键；也可以有独立有效关系表。不能用唯一(room_id,user_id,state)阻止同一用户多次退出／再加入。活动名额表只存未结束关系，ENDED历史成员仍是有效历史访问关系，不占活动名额。

Redis中的Session由Spring Session管理，不再把SQLite sessions表当Java的权威会话。账号注销必须跨实例撤销所有会话，并令旧快照的登录状态不能恢复使用。

## 2. 事务与锁顺序

把一个业务操作的判断和落库放在同一事务，避免“先查有名额、事务外再写”。统一锁顺序：先本次操作者user行，再room行，再members／record；涉及多个同类对象时按稳定ID排序。不要一条路径先锁room再锁user、另一条相反。对到期／注销的批量操作单独设计同序分批或有限重试，避免跨用户锁升级造成死锁。

- 创建／加入：锁操作者user，处理其原当前组是否到期，锁目标room，重新校验人数、状态、剩余天数、准备和共享，再写members及active_memberships。账号槽唯一冲突映射ALREADY_IN_ROOM；目标房间锁保证8人上限。
- 准备／编辑／退出／开始：锁room并校验version，和成员／权限修改同事务；编辑周期清全员准备；退出与交接同事务；最后一人关闭并使邀请不可加入。
- 开始：只允许LOBBY条件转换，提交时读权威时钟；旧预览拒绝。不同请求并发只一个转换成功；同成功键返回原结果。
- 保存记录：更新条件包含旧version，不先读后无条件覆盖；首次插入唯一冲突返回最新值。验证本人、ACTIVE、北京时间及截止，不在入队时“先接受以后再写”。
- 到期：读写接口与定时任务都可触发；更新条件status=ACTIVE保证幂等，释放对应活动名额。定时任务停机时接口仍拒绝过期写。
- 回执：领取时原子判断当前round、stage与当日回执，唯一约束防双端领取。GET预览不消费。
- 外部PNVS等待在事务外，核验租约短事务获取，携带lease token及dispatchId完成短事务；超时释放／标UNKNOWN，旧租约不可消费新码，锁等待和外部调用均有上限。

## 3. 幂等与当前授权

同一用户、key只允许同operation和同规范化bodyHash，重复返回持久result；不同请求体或操作409。同POST／PATCH profile共用operation。JSON对象字段排序不能导致语义相同却冲突，Java需固定规范化策略；未知结果重试由客户端保持同一body及key。

并发同key通过唯一约束、事务或专门锁协调，不允许执行两次后只保留一个回执。回执成功提交与业务写入同事务。重放必须仍验证身份与对象可见关系，不能让已退出者读取以前结果；但不可先用新日期／新状态拒绝本来已经成功的请求。注销后账号及回执均不可访问。

历史幂等记录当前没有自动清理；M1不自行加短TTL。未来清理需确定重试窗口及隐私策略。错误与重试返回值不保存他人的敏感字段。

## 4. Redis角色与故障行为

| 用途 | 本项目要求 | 故障／失效 |
| --- | --- | --- |
| Session | 两实例共享，7天绝对过期，退出当前会话、注销全部撤销 | Redis不可用返回明确503，不按匿名／默认用户放行；恢复不复活撤销账号 |
| 事件广播 | B10 实施：写入事务提交后向房间频道发布"谁做了什么"，各实例只推给本机 SSE 连接；事件不持久化 | 允许丢：断线或 Redis 不可用时前端退回 60 秒版本轮询；事件不是数据源 |
| 普通限流 | 原子计数＋TTL（Lua 一次执行），来源只信受控代理；付费短信日额度仍以 MySQL 为权威 | 认证／发送无法可靠限流时拒绝相关操作，不放行；不能无上限调用供应商 |
| 统计缓存 | B9 可选：缓存整份快照，键含环境／组／数据版本／业务日期／范围，鉴权永远在缓存之前，版本由写事务递增 | 写后换键而不是删缓存；重建单飞且有界；不可用回源并短时熔断；跨日换键，成员变化与注销递增版本 |

统计缓存的失效模型是"写事务递增 `rooms.stats_version`，新请求读新版本键"，因此不依赖跨实例失效广播，也不存在"删缓存后旧值写回"的时序窗口。旧键只由 TTL 回收；注销这类必须立即清除的场景，按每个房间维护的键索引集合精确删除，禁止 SCAN 与 FLUSHALL。设计细节见 [11 Redis 使用方案](11-Redis使用方案.md)。

事件广播是"至多一次"：频道不持久化、不重放、不保证跨实例顺序。因此事件只能表达"这个房间刚才有变化"，不能承载记录值；客户端收到后仍从快照接口读取数据，重连或降级时拉一次快照即可收敛。设计细节见 [12 实时动态与事件推送](12-实时动态与事件推送.md)。

敏感统计不放公共CDN。Redis不是业务事实来源；每日记录、准备、删除清单、付费短信计数不能仅在Redis。缓存里也不存身高或多余手机号。使用key前缀隔离新旧及local/test/sms-trial，不把FLUSHALL当清理策略。

M2的榜单与任务看10；仅用SET NX做“已提醒”不能保证最终不丢不重，不用分布式锁替代业务唯一约束。

## 5. 独立注销清单（M1必做）

推荐Java使用第二数据源／独立schema持久化privacy_journal.identity与events，采用不同备份生命周期；不随主业务快照回退。也可使用等价独立持久存储，但需通过恢复验收。只把清单另建一张业务表而与主库一起回滚不合格。

先持久写独立清单，再主事务完成删除并更新last_sequence；跨库不能假设一个本地事务覆盖两边。清单提交后主事务失败：用户请求返回明确待恢复／失败状态，不回报在线删除完成；本次及后台／重启重放完成前屏蔽该user身份与数据读取，不能只等下次重启。在多实例环境用用户删除状态／清单水位校验和写入串行化，防止另一个实例仍访问或写回已删除数据。

启动／恢复校验清单identity、完整性和序号；清单比主快照旧、缺失或不匹配均拒绝对外。读取、支持CLI、导出、缓存重建也不能绕过重放。事件应用幂等；清理所有本人关系、回执、记录、会话、缓存和异步结果，更新有关小组版本；其他成员含已删昵称的提示缓存也清理。

备份只恢复到隔离环境，先接入最新独立清单、重放删除、校验数据，再开放接口；会话不从旧Redis快照恢复。独立清单不等于备份物理删除，正式保存期限仍待定。

## 6. 迁移边界

M1从空的独立MySQL开始，使用合成种子，不读取var/private及线上库。未来迁移必须另交付dry-run工具、稳定ID／日期／枚举／精度映射、删除事件映射、汇总核对、切换和回滚步骤；手机号身份与同意记录不能擅自重建，旧Cookie失效要求重新登录。原SQLite和Node命令仍保留供原版本运行。
