# 12 实时动态与跨实例事件推送

更新：2026-10-30。状态：方案，未实施。这是 Redis 在本项目中最主要的真实用途；会话见 [11](11-Redis使用方案.md) 第 2 节，统计缓存见第 3–4 节。

## 1. 场景：队友刚打卡，我却要等 5 秒

产品定位是"和朋友一起坚持"，即时反馈直接影响打卡意愿。现在的做法是前端定时拉取：

- [02 页面与交互](02-页面与交互.md) 约定"前台约 5 秒轮询，失败退避最多 60 秒"；
- [App.vue](../apps/web-vue/src/App.vue) 的 `poll()` 每隔 5 秒调用 `refresh()`；
- `refresh()` 请求 `GET /rooms/:id?range=N`，拿到**整份快照**并整体替换。

因此"队友刚打卡"这件事，最坏要 5 秒才被看到，网络抖动退避后可能 60 秒；而在这 5 秒里，服务端和客户端都为此付了完整的代价。

## 2. 现状成本（估算，待压测确认）

| 指标 | 估算值 | 依据 |
| --- | --- | --- |
| 单份快照大小 | 几十 KB 到约 100 KB | 每个成员含范围点、全期统计、曲线点、记录明细，8 人 |
| 每次快照的 SQL | 约 10–12 条 | 鉴权、房间、成员，加 8 次逐成员记录查询 |
| 8 人同时在线的请求量 | 96 次完整快照／分钟 | 8 × 12 |
| 每台手机的空闲流量 | 每小时数十 MB | 快照大小 × 12 次／分钟 |
| 变更可见延迟 | 5–60 秒 | 轮询间隔与退避 |

**关键点：绝大多数请求发生时，数据一个字都没变。** 这是"拉模式"的固有浪费：客户端必须不断问"变了吗"，才能知道没变。

单次快照的计算并不慢（本机微基准约 0.11 毫秒），问题在于**反复问**。

## 3. 方案：把"拉"改成"推"

```text
写入事务提交（记录／加入／退出／准备／开始／到期）
        │  afterCommit
        ▼
  发布事件到 Redis 频道  room:events:{roomId}
        │
   ┌────┴─────┐
java-1 订阅   java-2 订阅
   │             │
本机 SSE 连接   本机 SSE 连接
   │             │
前端收到 change → 去抖 300ms → 拉一次快照
```

### 3.1 为什么必须是 Redis

SSE 连接分散在两个实例上：用户 A 连 java-1，用户 B 连 java-2。A 保存记录时请求落在 java-1，java-1 只能看到自己持有的连接，**根本不知道 B 连在 java-2 上**。没有共享通道，这条事件永远到不了 B。

这与会话共享是同一个根因：**两台机器要看到同一份状态。** 与用户多少无关，只要有两个实例就成立。

数据库做不到：让客户端轮询数据库"有没有变化"，正是要干掉的方案。

### 3.2 为什么是 SSE，不是 WebSocket

- 只需要服务端→客户端单向推送，不需要双向通道；
- `EventSource` 浏览器原生支持，自带断线重连；
- 走普通 HTTP，复用同源 Cookie 与现有鉴权，不需要额外的握手鉴权协议；
- Nginx 只需关闭缓冲，不必处理协议升级。

### 3.3 为什么是 Pub/Sub，不是 Stream／MQ

- 事件是**提示**，不是业务事实：客户端收到后仍然拉快照，真正数据来自接口;
- 因此允许丢、允许重复、不要求顺序，也不需要消费组、ACK、堆积治理;
- Stream／MQ 的持久化与重放能力在这里没有收益，反而带来消费位点、死信、堆积监控的复杂度;
- 需要"必达"的是 M2 的提醒与周报，那才用 RabbitMQ（见 [10](10-后续增强.md) X4）。

## 4. 事件契约

SSE 事件名与载荷：

```text
event: change
data: {"kind":"record.saved","actorId":"...","actorNickname":"小美","at":"2026-10-30T12:00:00Z"}
```

| kind | 触发时机 |
| --- | --- |
| `record.saved` | 新增或覆盖体重记录 |
| `member.changed` | 加入、退出、准备状态变化、资料（昵称／头像）变化 |
| `room.changed` | 改名、改周期、开始、到期、关闭、交接 |

约定：

- **不放体重数值**，只放"谁做了什么"。Redis 里不出现身体数据，事件也不承担数据同步职责。
- `actorNickname` 可放，因为对同组成员本来可见；注销后不再产生事件。
- 事件带 `v` 字段便于以后演进，但**不做版本兼容承诺**：客户端不认识 `kind` 就当成"有变化"处理。
- 频道名 `shangcheng:java:{mode}:room:events:{roomId}`，环境隔离靠前缀，与缓存一致。
- 控制频道 `shangcheng:java:{mode}:room:events:control`，用于跨实例踢线（见 5.3）。

## 5. 连接生命周期

### 5.1 建立

`GET /api/v1/rooms/:id/events`：

1. 复用 `SessionIdentity.requireUser` 与 `rooms.authorize`，**先鉴权再返回事件流**；非成员、已退出、已注销一律 401／403，不建立连接。
2. 响应头 `Content-Type: text/event-stream`、`Cache-Control: no-store`、`X-Accel-Buffering: no`。
3. 首帧发送 `event: ready`，让客户端知道推送通道可用，可关闭兜底轮询。

连接约束：

- 每用户每房间最多 1 条连接，新连接顶掉旧连接（多标签页不会放大连接数）；
- 每实例连接总数设上限，超过返回 503 与 `retryAfter`，不无限接收；
- 客户端断开、超时、异常都必须清理注册表与订阅。

### 5.2 订阅管理

- 实例只订阅**本机有连接**的房间；第一个连接进来时订阅，最后一个连接断开时退订。
- 不做"订阅全部房间"：房间数增长后订阅与回调都是无谓开销。
- 订阅回调只做一件事：把事件写给本机该房间的连接，不做数据库查询。

### 5.3 心跳与踢线

- 每 20 秒发送 `event: ping`，防止代理与中间层因空闲断开；
- 登出、注销时，本实例直接关闭该用户连接，并向控制频道广播 `{"kind":"revoke-user","userId":"..."}`，其它实例收到后关闭各自持有的该用户连接；
- 注销后的事件不再投递，迟到的重建任务不复活连接。

### 5.4 前端

- `EventSource` 连接 `/rooms/:id/events`；
- 收到 `change` 后 **去抖 300ms** 再拉一次快照，避免连续事件引发多次刷新；
- 收到 `degraded` 或连接失败时，退回 60 秒版本轮询，并显示一句"实时更新已暂停"；
- 收到 `ready` 或重连成功时，立即拉一次快照，停止兜底轮询；
- 页面隐藏时不重建连接（避免手机后台耗电），回到前台再恢复。

## 6. 发布时机与失败隔离

- 只在**事务提交后**发布（`TransactionSynchronization.afterCommit`）。事务回滚、校验失败、幂等重放都不产生事件，避免"幽灵事件"。
- 发布失败（Redis 不可用、序列化异常）只记 WARN 与计数，**绝不影响业务提交**；用户已经保存成功，不能因为推送失败而回滚。
- 事件里的 `at` 用服务端时间，客户端不依赖它做排序。

## 7. 降级：版本轮询

推送依赖连接与 Redis，必须有兜底。新增一个极小的只读接口：

```text
GET /api/v1/rooms/:id/version     →  {"dataVersion":12,"businessDate":"2026-10-30","status":"ACTIVE"}
```

- 复用同一套鉴权；
- 前端每 60 秒比对一次 `dataVersion` 与 `businessDate`，任一变化就拉快照；
- 不依赖 HTTP 缓存与 ETag：全局响应头是 `Cache-Control: no-store`，让客户端自己比较版本号更一致，响应体也只有几十字节。

降级触发条件：

| 情况 | 表现 |
| --- | --- |
| SSE 连不上或断开 | 前端立即进入 60 秒版本轮询，后台自动重试连接 |
| Redis 不可用 | 各实例向本机连接发送 `degraded`，客户端转轮询；事件丢失但数据仍可读 |
| 实例重启 | 连接断开，客户端自动重连并拉一次快照 |
| 代理不支持长连接 | 连接很快断开，自然退化为轮询，不报错 |

## 8. 与统计缓存的关系

- 事件到达后客户端只拉**一次**快照，而不是每 5 秒一次；这是流量下降的主要来源。
- 快照缓存（[11](11-Redis使用方案.md) 第 4 节）降低的是这"一次"的成本，属于可选的第二步；测不出收益就不上线。
- 顺序不能反：先有版本号与事件推送，缓存才有明确的优化对象。

## 10. 简历与面试

### 10.1 简历条目

> 把双实例部署下前端每 5 秒整包轮询改为事件推送：写入事务提交后经 Redis Pub/Sub 广播房间事件，各实例只推给本机 SSE 连接；空闲时零请求，数据变更 1 秒内到达；Redis 或连接不可用时自动降级为版本号轮询。

### 10.2 面试问答

1. **为什么不用 WebSocket？** 只需要服务端推、客户端收；SSE 自带重连、复用 Cookie 鉴权、代理更简单。双向通道在这里没有需求。
2. **为什么不用 Redis Stream 或 MQ？** 事件只是提示，允许丢；客户端收到后仍拉快照。Stream／MQ 的持久化、消费组、ACK 在这里没有收益，只有运维成本。
3. **消息丢了怎么办？** 允许丢。重连或收到 `degraded` 后拉一次快照，最终状态一定正确；这正是"事件不是数据源"的设计。
4. **会不会发假事件？** 只在 `afterCommit` 发布，回滚不会发。
5. **一个实例上的事件怎么到另一个实例？** 通过频道广播；实例不知道彼此持有哪些连接，所以必须共享通道。
6. **连接会不会泄漏？** 每用户每房间一条，新顶旧；断开、超时、注销都清理注册表并退订；心跳负责发现死连接。
7. **订阅所有房间可以吗？** 可以但不做：本机有连接才订阅，最后一个断开就退订，房间多了也不会累积开销。
8. **怎么证明有效？** 双实例脚本：连 java-1 与 java-2 两个 SSE 客户端，从任一实例写入，两个客户端都要在 1 秒内收到；同时记录空闲 30 分钟的请求数与流量，和 5 秒轮询对照。

## 11. 不做清单

- 不做事件持久化、不做断线补偿、不做 `Last-Event-ID` 重放：事件可丢，重连拉快照即可。
- 不承诺顺序与恰好一次：客户端只关心"有变化"，去抖后拉快照。
- 不推体重、身高、手机号等身体与身份数据。
- 不用事件通道代替业务接口：数据永远从快照与既有接口读。
- 不做 WebSocket 双向通道：没有客户端上行需求。
- 不在 M1 阶段引入：这是 B10，排在 M1 验收之后、M2 之前。
