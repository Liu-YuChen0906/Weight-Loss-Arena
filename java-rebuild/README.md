## 里程碑与批次

**M1：功能完整重构。**登录／资料、创建／邀请／加入、准备／开始、当天记录、个人分析、小组数据、复盘／历史、原有站内提示、导出／注销／支持全部可用；Vue 手机端完成；Redis 共享会话；双实例验证；不以新增功能代替原有功能迁移。

**M2：后端增强。**在 M1 验收后实现打卡榜、用户开启的每日提醒、异步周报，落地 MQ 可靠任务和 Redisson 调度协调。M1 的到期检查和原有第 3／4 天站内提示不依赖 MQ。MQ 依赖可在工程初始化提供，但不能把“容器启动成功”写成“已实现消息可靠性”。

**B9：读取优化批次（M1 之后、M2 之前）。**批量查询、数据版本、只读版本接口、前端版本轮询；统计缓存为可选项，测不出收益就不上线。它不改产品功能，因此不算 M1 功能缺口；M2 的榜单与周报复用这套版本号与缓存基础设施。方案见 [11](11-Redis使用方案.md)。

**B10：实时动态（B9 之后、M2 之前）。**把前端每 5 秒拉整份快照改为事件推送：SSE + Redis Pub/Sub，跨实例广播，Redis 或连接不可用时退回版本轮询。这是 Redis 在本项目中最主要的真实用途，方案见 [12](12-实时动态与事件推送.md)。

代码与需求的对应关系应由 07 记录；验收用 06 的 ID，不只报总测试数。已有 Node 的 86 项通过不能作为 Java 的通过证据。
