## 目标与范围

目标：把现有熟人小组体重记录产品改造成可运行、可演示、可验证的 Java 全栈项目，用于展示后端工程能力和完整产品交付能力。

采用模块化单体，一个 Java 项目内按账号、组队、记录、统计、通知、报告划分模块；通过两个应用实例验证共享状态和并发行为。双实例不等于微服务或高可用，Redis、MySQL、RabbitMQ 首期均可单节点。

保留现有产品规则、视觉和基本流程。先复用原网页验收 Java 接口，再逐页迁移 Vue，避免前后端同时重写难以定位问题。不修改 prototype/。新代码建议放 apps/java-api/、apps/web-vue/，现有实现保留作行为参照。

本计划不执行线上替换、真实短信发送或真实用户数据迁移。Java 版先用独立数据库和合成数据；旧试用版保持独立。未来切换前另做备份、字段映射、注销清单重放、会话失效和回滚演练。

## 技术选择及具体用途

| 技术 | 本项目中承担的工作 |
| --- | --- |
| Java 21、Spring Boot | Java 后端、参数校验、接口、事务、定时任务；实施时选择与 Java 21、相关依赖兼容且仍受维护的稳定版本，记录锁定版本 |
| MySQL、MyBatis-Plus、Flyway | 业务持久化、查询分页、数据库事务、可重复执行的结构升级 |
| Spring Security、Spring Session + Redis | Cookie 会话登录、权限与 CSRF，两个实例共享会话；退出后跨实例失效 |
| Redis | 共享会话、接口限流、小组打卡榜和统计缓存；数据库为业务事实来源 |
| Redisson | 两个实例之间协调提醒扫描与缓存重建；数据库唯一约束兜底，锁不是唯一正确性保障 |
| RabbitMQ、Spring AMQP | 周报生成、提醒分发异步执行，具备发布确认、消费确认、有限重试和失败任务处理 |
| Vue 3、TypeScript、Vant、图表库 | 手机端页面、表单、统计图和异步任务状态展示；延续现有视觉 |
| Docker Compose、Nginx、CI | 启动依赖、反向代理两个实例、持续构建与自动检查 |

优先把上述技术做实。首期不加入微服务、服务注册中心、Elasticsearch、推荐算法、支付和模型调用；Excel、复杂线程池与 CompletableFuture 在出现实际需要后再评估。

## 新增功能与业务规则

### 1. 小组打卡榜

- 按当前期次有效记录天数排序，同日修改体重不重复加分；同分并列，不按减重速度排名。
- Redis ZSet 保存派生排名，MySQL 保存原始记录。保存记录后触发更新或失效；并发事件采用版本校验或串行重建，避免旧结果覆盖新结果。
- Redis 缓存丢失时可从数据库重建；不可用时榜单回源，不能阻止保存体重。缓存设有效期，组员变更和注销同步清理。
- 小组成员才能查看，结束期按既有历史访问规则处理。明确榜单为最终一致，不承诺瞬时跨端一致。

### 2. 用户主动开启的每日提醒

- 默认关闭；用户开启后按北京时间固定时点检查当天是否已记录。提醒只针对有效参与者。
- 首期投递站内通知，沿用并梳理已有提示和领取回执机制，不再造一套冲突规则。站内通知只能在打开应用时看到，不宣传为手机推送。
- 调度器扫描未完成提醒，形成数据库任务与待发事件，再经 MQ 分发。消费者执行前再次检查是否已打卡、是否关闭提醒、是否退出或注销。
- 同一用户、期次、业务日期、提醒类型只生成一条通知，数据库唯一约束保证；Redis 可辅助限流或减少重复处理，不能单独承担防重。
- 外部邮件、短信、订阅消息仅作后续扩展；接入后需另外处理外部发送回执与结果未知，不承诺跨系统恰好一次。

### 3. 异步周报

- 用户查看本人本期某周报告，包含打卡次数、体重趋势及允许共享的小组汇总，不提供医疗判断。
- 请求后立即返回任务编号，前端展示“生成中／完成／失败可重试”，轮询状态取得结果，不能只转圈无结果。
- 同一用户、期次、周区间和数据版本复用任务；报告与任务结果存 MySQL，Redis 缓存报告读取结果。
- 历史记录更正后报告标记过期并可重新生成；生成任务以数据版本识别，防止旧任务覆盖新报告。
- 消息只带任务 ID 等必要字段，消费时再读有权限的数据；注销后停止生成并删除对应报告及缓存。

## 关键实现与验证约定

1. 入组正确性优先由 MySQL 事务、账号活动参与约束、必要的行锁／条件更新保证，不依赖 JVM 内存锁。测试同账号并发加入不同小组、同组同时加入、重复请求；若保留或新增人数上限，再测试最后一个名额竞争，不擅自改变人数规则。
2. 记录表约束用户、期次、业务日期唯一；保留既有版本冲突与重复提交回执语义。核对单位换算、北京时间日界和当前目标算法。
3. Redis 限流采用原子操作和明确过期时间；短信等付费全站额度仍有持久化账本，重启和 Redis 清空不能重置。真实短信适配迁移时处理跨实例核验租约、流水号和迟到回执；演示先用替身。
4. 同一次 MySQL 事务写入任务和 Outbox 待发事件；后台补发直到确认或转入可见失败状态。使用持久队列、持久消息、发布确认与不可路由返回处理；业务处理成功提交后再确认消费。
5. 默认有限重试，超过次数进入死信／失败任务状态；提供受鉴权保护的失败任务查询与重试，避免无限重入队。定时补扫未完成任务，允许消息至少一次到达，业务效果通过数据库约束防重。
6. Redisson 锁设置合理等待和释放策略。模拟进程退出、锁过期、两个调度器重复运行；唯一任务键兜底，不能把“拿到锁”当成一定只执行一次。
7. 使用真实 MySQL、Redis、RabbitMQ 的隔离集成环境验证关键行为；浏览器贯通页面、API、数据库和报告结果。测试结束检查遗留任务，不把 Mock 单测当成链路验证。
8. 性能测量固定合成数据、资源与并发，记录响应时间分位数、吞吐、错误率、SQL 次数及缓存命中率；对比相同条件下启用缓存与回源。不预先承诺 QPS、用户规模或提升比例。
9. 提供 requestId、任务 ID、耗时和重试日志，不记录验证码、手机号明文或体重明文。区分服务启动、依赖就绪、消息积压和失败任务。
